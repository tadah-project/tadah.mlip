## [1.6.0] — unreleased

### Added
- **Blueprint field `command_only`** (`BlueprintKey::command_only`, a boolean): a key that only the commands whose `[TASKS.*]` table lists it read, an option of their command line or a key of their configuration file, never a key of a model or a potential, and, apart from `OUTFILE` of `tadah train`, never a key of a training configuration. The blueprint marks 79 keys so: the options of `tadah predict`, `data`, `analysis`, `properties`, `explain` and `refit` that no model reads (`ANALYTICS`, `INDEX`, `STRUCTURE`, `POTENTIAL`, `TYPE`, `RANGE`, `EDIT`, `RETARGET`, ...), every `REFIT_*` key and the other keys of `tadah refit` (`EAM`, `SETFL_OUT`, `N2B`, the `OPTIMIZER`, `INIT`, `EXPLORE`, `REFINE` and `FUSE` blocks, ...), and `OUTFILE`, which `tadah hpo` and `tadah analysis check_bounds` do not read. `commands_reading_key(key)`, `command_key_role(key)`, `command_key_text(key)` and `task_command_words(task)` (`blueprint_parser.h`) name the commands that read a key for a message: a command whose table retires the key (an option it refuses with the reason, `--rescale` of `tadah data balance`) does not read it, and a key whose `cli_long_flag` does not start with `-` is the argument of its command (`OPTION is the argument of tadah explain`).
- **`CoreUserConfigParser::set_command(task)`**: the command whose configuration file the parser reads (its blueprint task name). A line of a `command_only` key that the command does not read is an error at its line, in the file and in its `CONFIG` includes (`Key ANALYTICS on line 3 of config.train is not accepted here: ANALYTICS is the option --analytics (-A) of tadah predict, not a key of a configuration file of tadah train`); Tadah.MLIP's `TaskFactory` sets it for the file of `-c`.
- **The error scales of a fit: `ESIGMA`, `FSIGMA`, `SSIGMA`, `ENORM` and `ENERGY`** (blueprint keys; Tadah.MLIP applies them, see its entry). A fit minimises the sum over its observations of priority × (residual / error scale)², plus the `LAMBDA` penalty: the energy of each structure per atom (`ENORM ATOM`, the default) or per sqrt(atom) (`ENORM SQRT`) with `ESIGMA` in meV/atom (default 1), each force component with `FSIGMA a [b]` in eV/Å (default 0.1 0) and the nine entries of each stress tensor with `SSIGMA a [b]` in GPa (default 0.5 0), each error scale sqrt(a² + (b M)²), M the RMS of the structure's own reference values; `ENERGY false` fits forces or stresses only. Every potential a fit writes has a line of each, the defaults included. Their help, that of `WDBFILE` and `LAMBDA` and that of the retired keys links to the documentation page *What a Fit Minimises*, which gives the rule and every conversion (`tadah explain` shows the link as the page's title). Tests: `test_blueprint_retired.cpp` (`Blueprint: the error scales ...`), `test_retired_keys.cpp` (`The error scales, ENORM and ENERGY are keys of a configuration`).
- **The help of `tadah train` and `tadah hpo` describes the balance table of a fit** (Tadah.MLIP): what it holds (the error scales, and per quantity and dataset the observations, the RMSE, the root mean square of residual over error scale, the share of the minimised sum and the effective parameters), where it is kept (the end of the training record of the potential of `tadah train` and of `best_pot.tadah`) and what it costs (one pass of the order of n p² and memory of the order of p², of 1024 rows and of three rows per dataset, computed by `tadah hpo` only for an evaluation whose loss may make it the best). `dgeqrf_` (`lapack.h`), the QR factorisation the table streams the rows of a fit through.
- **A retired state of a key** (blueprint field `retired`: a table of `reason`, `replacement` and `conversion`, and the optional `by_deletion`, true for a key that nothing replaces, whose every line a deletion converts, and `unconverted`, true for a key that no key converts and whose deletion changes the fit (`EWEIGHT_TEMP`), the two not both true; `BlueprintKey::retired`, `isRetired()`): a retired key has no `default_value` and no examples (BlueprintParser refuses either, and a key that is deprecated as well), may keep its command-line option to give the conversion, and is never suggested for a misspelt key (`findClosestKey`). CoreUserConfigParser checks a retired key's value, records its line on the Context it returns instead of storing the key (`Context::retired_keys()`, `record_retired_key()`: copies, `merge()` of either side, `serialize()` and `deserialize()` keep them, and neither `operator<<` nor `write_potential()` writes them), and gives one notice per parse that lists the retired lines it read, on standard error or to the `IgnoredKeyNoticeCapture` of `pair_style tadah` (`report_key_notice()`, `key_notice.h`): `WARNING: Retired keys EWEIGHT (line 8 of old.tadah), FWEIGHT (line 10 of old.tadah) ... are ignored by a prediction, as they change nothing it gives, and refused by a fit (tadah explain EWEIGHT, ... give the reasons and the conversions).`, which says what each does, as a fit's configuration gets it too, before the fit's refusal `Context::add()` and a read of a retired key refuse it with its conversion. `retired_keys.h` gives the texts: `retired_key_text()`, `retired_keys_notice()`, `retired_keys_refusal()` (which names a line of more than six values by its first three: `WCOV 28 1.2e-05 3e-07 and 782 more values (line 40 of pot.tadah; converted by deleting the line)`, marks each line of a `by_deletion` key so and gives that key's reason, marks a line of an `unconverted` key `no key converts it` and gives its reason, and ends with the converted keys in place of the lines, or the marked lines deleted, and a line no key converts deleted, adding that no key reproduces it: `With the converted keys in place of the others and the EWEIGHT_TEMP line deleted (...), the configuration trains, and no key reproduces the EWEIGHT_TEMP line; no coefficients were fitted.`) and `require_no_retired_keys()`, which every fit calls (Tadah.MLIP). Tests: `test_blueprint_retired.cpp`, `test_retired_keys.cpp`.
- **A key line rule for a parse** (`iuser_config_parser.h`; Tadah.MLIP's dataset-keys entry): `CoreUserConfigParser::parse(filename, rule, skipped)` reads and checks every line as `parse()` does, and does not store a key line that the `KeyLineRule` selects by the keys of the lines of the file it is in: it is listed as a `SkippedKeyLine` (the file, the line, the key, the values). A file a `CONFIG` line includes is read under the same rule, by its own lines; the words of a block's body (`INIT ... ENDINIT`) are not the file's keys. The lines no parse stores, the run settings of a potential (the BREAKING entry under *Changed*), are listed too. So is a line of a retired key that the rule selects, which is then not recorded as a retired line. Tadah.MLIP's `TaskFactory` uses it so that a potential's lines of the keys of its training record but `DBFILE` (those that prepared its training data and the run settings) are not read for a retrain or `tadah hpo -c`. Tests: `Config parser: a key line rule skips the lines it selects by the keys of the file they are in`, `Config parser: a potential's run setting lines are not stored, and its VERBOSE sets no log level`, `A retired key's line that the caller's rule selects is the caller's`.
- Tests: `tadah.core_headers` (`ctest -L headers`, cmake-tools' `tadah_add_header_check`) compiles every header of `include/` and the generated `blueprint_tadah.hpp` on its own and twice in a row, with what a user of `tadah.core` gets. Every CORE header passes.
- Tests: `tadah.core_text` (`ctest -L text`, cmake-tools' `tadah_add_text_check`) reads the text files of the repository (those git tracks or would track, in a clone) and fails on a line that carries a person's initials, a reference to co-workers, a decision attributed to the code's owner, the name of an AI tool, a note kept outside the repository or filler wording.
- **`parse_one_based_indices(values, total, who, counted)`** (`utils.h`): the checked 1-based index list of `parse_dataset_indices` (the same grammar and refusals; the bounds are checked before a range is expanded), whose bound message ends with `counted`, what the indices count: `tadah analysis bfunc: index 9 (in '2-9') is outside 1-4 (the D2_Blip basis has 4 functions)`. `parse_dataset_indices` is `parse_one_based_indices` with `the dataset has <N> structures`. `tadah data print`, `analysis descriptor` and `analysis bfunc -i` use them (see Tadah.MLIP).
- **`parse_fixindex(ctx, n_weights)`** (`utils.h`), the one reader of `FIXINDEX`: the weights the `FIXWEIGHT` values pin, 1-based and in declaration order (the i-th value pins the i-th weight). The values of `FIXINDEX` form one list with the grammar of `parse_one_based_indices` (entries separated by commas or whitespace: `FIXINDEX 13 14`, `13,14` and `13, 14` are the same list; `i`, `a-b`, `a-b:step`), whose tokeniser the two share. Refused, each with one message naming the text: a lone `FIXINDEX` or `FIXWEIGHT` (the trainers' text); an empty entry, a token that is not an index, a descending range and a step of 0 (`FIXINDEX: index '14-13' is a descending range (FIXINDEX takes 1-based weight indices i, a-b or a-b:step, separated by commas or spaces)`); index 0, and, when the weight count is given, an index above it (`FIXINDEX: index 9 (in '2-9') is outside 1-4 (the model has 4 weights)`), checked as each entry is read; a weight named twice among the first n + 1 indices, n the number of `FIXWEIGHT` values (`FIXINDEX 13,13,14 names coefficient 13 twice; each FIXWEIGHT value fixes one coefficient ...`; **BREAKING**: the lenient reader removed the repeat with a warning), so every list with a repeat that names no more distinct weights than `FIXWEIGHT` has values (`13,13,14` with two values, one per distinct weight, as with three); otherwise a number of indices other than the number of `FIXWEIGHT` values (`FIXINDEX 1,2,3 has 3 indices but FIXWEIGHT has 1 value; they must pair 1:1 (...)`), counted per entry, with no more than n + 1 indices expanded, so `1-4000000000` is refused at once. Empty without the keys. MODELS' trainers, MLIP's weight provisioning and BIAS composition check and HPO's `OPTIM FIXWEIGHT` mapping and startup checks read `FIXINDEX` with it (see those changelogs). Test: `test_fixindex.cpp`.
- **Blueprint field `exact_in_potential`** (`BlueprintKey::exact_in_potential`): a key whose numbers a potential file records exactly whatever NUMERIC is, because a load checks them exactly. `Context::write_potential` writes each non-integer number of such a key below 17 significant digits as the shortest text that reads back as the same double (`reformat_double_token_exact(tok, buf, cap)`, `number_format.h`), and with NUMERIC digits from 17 on (exact). `BlueprintParser::buildKey` refuses a value that is not a boolean (`'exact_in_potential' must be true or false in key: ...`) and `true` on a key without a DOUBLE position. The blueprint sets it on `RCUT2B`, `RCUTMB`, `CGRID2B`, `CGRIDMB`, `SGRID2B` and `SGRIDMB` (the `NUMERIC` entry under *Changed*); `exact_in_potential_keys()` lists them, in alphabetical order. Test: `test_blueprint_exact_in_potential.cpp`.
- **`IgnoredKeyNoticeCapture`** (`key_notice.h`): while one lives on a thread, `report_ignored_key()` (the notice of a deprecated key and of a key without effect) gives it the notice line instead of writing it to standard error, for a caller that writes the notices itself. `report_ignored_key_once()` gives a capture each key once, also a key the process reported before it, and writes a key to standard error once per process, as before. `pair_style tadah` loads a potential under one and writes the notices as LAMMPS warnings, so each LAMMPS instance's log.lammps has them (Tadah.LAMMPS). Test: `test_key_notice.cpp`.
- **`intercept_columns_by_Z(ctx)`** (`intercept_layout.h`): the intercept column of every atomic number 0 to 118 in ATOM order, -1 for an element ATOM does not list (the per-atom lookup table of MLIP's `DescriptorsCalc` and of pair_style tadah, so the mapping lives in one place). Test: `test_intercept_layout.cpp`.
- **`Matrix3d * Matrix3d`**, the row-by-column matrix product.
- **`parse_dataset_indices(values, total, who)`** (`utils.h`): the checked 1-based structure indices of `tadah data sample` and `data balance -i`. The values form one list (entries separated by commas or whitespace, spaces allowed around `-` and `:`), repeated indices are removed, and an empty entry, a token that is not an index, a descending range, a step of 0 and an index outside 1 … total are refused, naming the text; the bounds are checked before a range is expanded.
- **`CoreUserConfigParser::refuse_keys({key → reason})`:** a line that sets a refused key, in any letter case and in a `CONFIG` include too, is an error naming the key, the line, the file and the reason (`Key FORCE on line 2 of val.tadah is not accepted here: …`). HPO's `--validation` file refuses every key but `DBFILE`, `EFILTER`, `FFILTER` and `CONFIG` this way.
- Strict index parsing for indexed configuration keys.
- Blueprint field `allowed_values` (`BlueprintKey::allowed_values`, `isAllowedValue()`): the only values of a single-string key, matched without regard to case. `BlueprintParser::buildKey` requires a non-empty list of non-empty strings on a `STRING` key with `value_N = [1]`, and the key's default and examples among them. `CoreUserConfigParser` rejects another value at the line that sets it, naming the file (`Invalid value for key EMBF0 on line 3 of pot.tadah: 'ZEROO' (allowed: ZERO, FREE)`; lines that come from no file give the line alone), and `validateWithBlueprint` (the command-line path) refuses it with an `Allowed values` log line; `validateSchemaOnly()` is the type check alone. `EMBF0` is the first key that uses it (`value_format` `ZERO|FREE`). Test: `test_blueprint_allowed_values.cpp`.
- Deprecated configuration keys: the blueprint field `deprecated` holds the reason and the replacement. `CoreUserConfigParser` accepts a deprecated key, checks its value against the key's format, writes one notice per key and process to standard error (`WARNING: Deprecated key MBLOCK is ignored: …`, through `report_ignored_key_once`, however many lines, `CONFIG` files or parses read it) and does not store it. The notice bypasses the `Logger`, so neither the log level nor a `VERBOSE` line suppresses it, and `pair_style tadah` in LAMMPS (which leaves the `Logger` at `ERROR`) shows it too, as a LAMMPS warning in `log.lammps` at each `pair_coeff`, not on standard error (`IgnoredKeyNoticeCapture`, above). `BlueprintParser::buildKey` rejects a deprecated key with a `default_value` (`Context::contains()` would insert it, and it would reappear in every written potential), a CLI flag or examples (the configuration-keys page and the invalid-value error would show how to use it; `examples = []` overrides those of an inherited `TYPES` table), and `findClosestKey` never suggests one.
- `EMBF0` key (`ZERO` | `FREE`, default `ZERO`): the DM_REAM embedding reference (see Tadah.MODELS). It takes `ZERO` or `FREE` only, in any case (`allowed_values`, below); any other value is an error at its line. STRING key with an explicit blueprint default, so the DM_REAM constructor materialises it into the model Context and every DM_REAM potential is written with an explicit `EMBF0` line. `refit_constrain_f0` description: effective under `EMBF0 FREE` only.
- **BREAKING — `RHOFORM` key (`SIGNED` | `NONNEG` | `MONOTONE`): the DM_REAM density form (see Tadah.MODELS), mandatory and without a default.** A STRING key deliberately given no `default_value`: every DM_REAM potential and configuration must declare it, and nothing supplies it implicitly. Readers go through `Context::has_stored()` / `stored_value()` only (a `Context::get` on the absent key would log a spurious ERROR before throwing). Its `allowed_values` are `SIGNED`, `NONNEG` and `MONOTONE`, in any case (`value_format` `SIGNED|NONNEG|MONOTONE`): another value is an error at its line, naming the file, as for `EMBF0` (`Invalid value for key RHOFORM on line 24 of pot.tadah: 'SQUARE' (allowed: SIGNED, NONNEG, MONOTONE)`), also in a potential without a DM_REAM block. The `AMPGRIDMB` description says what the amplitudes multiply under each form, and the help of `tadah refit` lists `RHOFORM` as a required refit key. Test: `test_blueprint_allowed_values.cpp`. **Migration:** a DM_REAM potential written before tadah 1.6.0 gives its 1.5.0 energies with both `RHOFORM SIGNED` and `EMBF0 FREE` added (`RHOFORM SIGNED` alone keeps the density; the absent `EMBF0` reads as `ZERO`). Binaries older than the key refuse a potential that carries it (`Invalid key: RHOFORM`).
- `number_format.h`: lossless number text. `format_roundtrip()` gives the shortest text that reads back as the identical double (`std::to_chars`); `format_sig()` / `format_sig_chars()` give locale-independent `%.{N}g` (a finite value never renders to text that overflows); `reformat_double_token()` re-renders one token; `to_double()` / `parse_number()` parse like `std::stod`, except that an underflowing literal is always a value (the subnormal or ±0): `std::stod` throws `out_of_range` for one whenever the C library's `strtod` reports the underflow (glibc does for every literal whose value it rounds, such as `1e-310`); `resolve_pot_digits()` / `pot_digits_warning()` implement the potential-file precision rule below.
- `to_string_lossless()` (`utils.h`) for scalars, strings and ranges. `to_string(x, n)` is for human-facing text only.
- `Context::has_stored()` / `Context::stored_value()` look a key up without inserting its blueprint default.
- `Context::write_potential(os, sig_digits)`, the potential-file writer: the `operator<<` layout, never a NUMERIC line, and every non-integer number of a key with a DOUBLE position rendered with `sig_digits` significant digits, but below 17 digits the numbers of the keys the blueprint marks `exact_in_potential`, the cutoffs and radial grids, which are written exactly (the `NUMERIC` entry under *Changed*); integers, strings, `LIN`/`GEOM`, bools, index patterns and inf/nan are written verbatim.
- `key_notice.h`: the notice of a key that is accepted but has no effect. `report_ignored_key(subject, reason)` writes `WARNING: <subject> is ignored: <reason>` to standard error in one insertion (not a `Logger` message, so neither the log level nor `VERBOSE` hides it; under `pair_style tadah` an `IgnoredKeyNoticeCapture` takes the line, above); `report_ignored_key_once(key, subject, reason)` writes it at most once per key and process (thread-safe), and `ignored_key_reported(key)` says whether it has. The deprecated-key notice of `CoreUserConfigParser` goes through `report_ignored_key_once` (the text is unchanged; once per key and process, as for every ignored key: parsing a potential with `MBLOCK 64` and `EMBF0 FREE` twice in one process prints each notice once); MODELS reports `EMBF0` and `RHOFORM` without a DM_REAM block through `report_ignored_key_once`, and the `EMBF0` and `RHOFORM` descriptions say so. Test: `test_key_notice.cpp`.
- `parse_decimal_normal()` (`number_format.h`): the number grammar of the hpotarget file, `parse_decimal_finite()` whose value is also zero or a normal double (a subnormal such as `1e-310`, and a nonzero literal that underflows to 0 such as `1e-400`, are refused; the tests are on the bits). HPO's `parse_number` reads hpotarget numbers with the same grammar, and MLIP's `tadah refit --retarget` reads its `--pct` and `--set` numbers with it, so every number it writes into an hpotarget is one `tadah hpo` reads back. Test: `test_number_format.cpp`.
- `RETARGET_RHOFORM` key, the `--rhoform SIGNED|NONNEG|MONOTONE` option of `tadah refit --retarget` (`allowed_values`; needs `--retarget`): the density form of the potential an hpotarget searches around, for a file written without the `RHOFORM` header line (see Tadah.MLIP). The `refit` help and the `retarget` key describe it, the `RHOFORM`/`EMBF0` rules of the `--edit` and `--retarget` configurations, and the checks on `--pct` and `--set` (the hpotarget number grammar, an `OPTIM` line on each `--pct KEY`, finite `--set` bounds within the density form's rule). The `analysis check_bounds` help says how each corner is built and that a DM_REAM seed must declare `RHOFORM`. Test: `test_blueprint_allowed_values.cpp`.
- **Structured `DESCRIPTOR` blocks.** Repeatable `DESCRIPTOR … ENDDESCRIPTOR` blocks are captured, with nested boundaries and source locations, across `CONFIG` includes and Context transports. `Context::merge` gives them the precedence of a key: a kind of block the overriding context declares replaces the base context's blocks of that kind (`Context::BlockMerge::Replace`, the default, under `allowOverwrite`); the blocks of a `CONFIG` include stand at its `CONFIG` line, after those above it (the configuration is the concatenation of its lines, *Changed*), and `BlockMerge::Append` composes two contexts the same way. Test: `Context::merge gives structured blocks the precedence of a key`.
- **`Context::key_lines()`, `Context::set_key_lines()`, `KeyLine`**: the lines that gave each key its values, in line order, each with where it is, as an error of the line names it (`line 3 of pot.tadah (CONFIG on line 2 of run.train)`), whether it is a line of a potential, a file whose own key lines give `WEIGHTS`, the file it is in (`source`, as the parse names it: the file given to the parse or the path of the `CONFIG` line that includes it), the number of values it gave (`values`), the number of the line in its file (`line`) and its number among the lines of its file that hold more than blanks and a comment (`ordinal`), so that two lines of one potential file are told apart from lines of two files, and lines one after another, with only comments or blank lines between them, from lines apart. `CoreUserConfigParser` records them on the Context of a parse; copies, moves and `merge()` carry them, and a change the program makes to a key's values drops them. `operator==`, `serialize()` and the writers do not read them. `Context::written_line_sizes(key, values)` gives the lines `write_potential()` and `operator<<` write the values of a key on, as the number of values of each line (a new `TYPE2B` or `TYPEMB` line at each value after the first that names a descriptor, the blueprint's `formatting`, or that is the ID of a `DESCRIPTOR` block: `D2_mJoin D2_Blip 2 2 Ta Ta D2_BP 2 2 Ta Ta` on lines of 1, 5 and 5 values, `DM_EAD 0 1 1 Ta Ta @ta` on lines of 6 and 1, `@ta @tb` on lines of 1 and 1, each a line the parser reads), the rule the writer uses, so that MODELS judges the `TYPE` lines of a potential file by what the writer writes. Tests: `Context: the lines of a key follow its values`, `Config parser: the Context records the lines that gave each key its values and whether each is a potential's line`, `Context: written_line_sizes gives the lines the writer writes a key's values on`.
- Component spatial radii are kept when ordinary keys refresh the neighbour-range metadata. Two configuration keys are added: `REFIT_PAIR_BASIS`, the pair basis of a `tadah refit` with `DESCRIPTOR` blocks (default Blip5), and `REFIT_COMPONENT_ITERATIONS`, the iteration limit of the compact fit of `DM_Embed` components (`REFIT_MODE compact` with `DESCRIPTOR` blocks; default 60).
- **`CHECK`, the `--check` flag of `tadah hpo`** (blueprint, `[TASKS.hpo]`; boolean, default `false`): `tadah hpo --check`, or `CHECK true` in a configuration file without `WEIGHTS`, makes the startup checks of the run and prints a summary, with the warnings and hints the run writes to its journal at startup, without an evaluation or a file (Tadah.HPO). A setting of the run, as `HPOTARGET` is: `run_setting_keys()` lists it (the entry on run settings under *Changed*), so no parse stores the `CHECK` line of a potential, a file whose own key lines include `WEIGHTS`: `tadah hpo -c` of such a file runs (Tadah.MLIP names the line in a WARNING, and `CHECK` then goes on the command line or in a configuration file that includes the potential with `CONFIG`); a `CHECK true` line in a training configuration without `WEIGHTS` makes `tadah hpo -c` a check. No potential has a `CHECK` key line: the training record of a `tadah train` or `tadah refit` potential lists the `CHECK` line of its configuration, and that of a `tadah hpo` potential none (Tadah.MLIP, Tadah.HPO). The examples of `tadah hpo` show it, and its help describes all of this. Tests: `test_blueprint_parser.cpp`, `Config parser: a potential's CHECK line is not stored, a training configuration's is`.
- **Each line of a deprecated key that a parse reads is recorded on the Context it returns** (`Context::record_deprecated_key()`, `Context::deprecated_keys()`: the key, the file, the line number, the values and the line), kept apart from the keys with the retired lines: copies, `merge()`, `serialize()` and `deserialize()` carry them, and no writer writes them; `retired_keys()` lists the retired lines only. A fit refuses a Context that records one, naming the line and the file (Tadah.MODELS `require_no_inert_keys`, Tadah.MLIP `require_no_unused_keys`). Test: `test_deprecated_keys.cpp`.

### Changed
- **BREAKING — `OUTFILE` is a key of the commands whose output file it names** (`command_only = true`): `tadah train`, `refit`, `predict`, `properties pairwise` and the `data` and `analysis` commands whose tables list it. An `OUTFILE` line in a configuration file of `tadah hpo` or `tadah analysis check_bounds` is refused at its line (`Key OUTFILE on line 3 of config.train is not accepted here: OUTFILE is the option --outfile (-o) of tadah analysis bfunc, ..., tadah refit and tadah train, not a key of a configuration file of tadah hpo`); 1.5.0 read the line in a configuration of `tadah hpo` and wrote no file of its name. A configuration shared by `tadah train` and `tadah hpo` converts by deleting the line; `tadah train -o` names the potential file. A configuration file of a command whose `-c` needs the option of a key on the command line refuses a line of that key at its line (`config_needs_option`, `blueprint_parser.h`), also of a key that another command reads from its configuration file: `OUTFILE` of `tadah analysis dataset_stats` and `tadah analysis suggest_bounds`, whose `-c` needs `-o`, `RANGE` and `TYPE` of `tadah analysis bfunc`, whose `-c` needs `--range` and `--type`, and `HPOTARGET` of `tadah hpo` (the entry below) (`Key OUTFILE on line 33 of cfg.tadah is not accepted here: OUTFILE is the option --outfile (-o) that --config (-c) of tadah analysis dataset_stats needs on the command line, not a key of a configuration file of tadah analysis dataset_stats`); 1.5.0 read such a line and took the option's value in its place, without a message. Such a configuration converts by deleting the line. In a potential, an `OUTFILE` line is a setting of the run that wrote it and is not read (`CoreUserConfigParser` keeps the rule of a run setting there: the line is listed among the lines not read, without the notice of a key of another command).
- **BREAKING — a configuration file of `tadah hpo` refuses an `HPOTARGET` line** at its line (`Key HPOTARGET on line 2 of config.train is not accepted here: HPOTARGET is the option --hpotarget that --config (-c) of tadah hpo needs on the command line, not a key of a configuration file of tadah hpo`), by the rule of a key whose option `-c` needs (the entry above), which holds for a key that another command reads from its configuration file: `tadah analysis check_bounds -c` reads an `HPOTARGET` line. `tadah hpo -c` needs `--hpotarget`, whose file 1.5.0 took in place of the line without a message. (integers are written exactly, and so are the numbers of CGRID2B, CGRIDMB, RCUT2B, RCUTMB, SGRID2B and SGRIDMB, which a load checks exactly): the other values do not round-trip exactly ...`). A number that a low NUMERIC (1–5, 10, 11, 15 or 16) would round past the largest double, the `DBL_MAX` `NSTDEV` sentinel of a constant descriptor column (`1.8e+308`), is truncated toward zero (`1.79e+308`), so the file loads. The copy constructor, the copy assignment and the pointer constructor copied `size() * stride` doubles from the first value and kept the stride (a move out of a view took the view's pointer, as a move out of a column did: the entry above): a copy of a strided view, such as `Matrix::row(r)` (the `cols()` values of row r, `rows()` apart), and the copy that `const Matrix::row(r)` returns read r doubles past the end of the matrix's storage (a heap-buffer-overflow), and the copy's `data()` and `begin()` to `end()` were not the row's values (`{20, 1, 11, 21}` for row 2 of a 3 × 4 matrix with values 10 r + c, not `{20, 21, 22, 23}`). A copy of an owner made with a stride (`aed_type(n, s)`) now has stride 1 as well, with the same values. The copy assignment makes its copy before it frees its old buffer: an owner assigned a view of its own values read the freed buffer. No Tadah module copies a strided view (the callers of `Matrix::row` are tests). Test: `test_aed_type.cpp`.
- **`aed_type` iterates through its stride, and `Matrix::row()` and `col()` return views whatever the compiler elides.** `begin()` and `end()` were `data()` and `data() + size()`, so a range-for or a standard algorithm over a strided `aed_type`, `Matrix::row(r)` (`cols()` values `rows()` apart) or an owner made with a stride (`aed_type(n, s)`), visited the `size()` doubles after its first value: row 0 of a 3 x 4 matrix gave `M(0,0), M(1,0), M(2,0), M(0,1)`, and a loop that wrote through a row view wrote those. A key whose STRING values are names (blueprint field `names`, `BlueprintKey::names`: `ATOM`, `atompair`, `RCTYPE2B`, `RCTYPEMB`, `TYPE2B`, `TYPEMB`, `MODEL`, `WATOM`) refuses a comma or a `+` in a name (`ATOM Ta,Nb`, `RCTYPE2B Cut_Cos,Cut_Tanh`, `TYPE2B D2_Blip 4 4 Ta,Nb Nb,Ta`), which it kept as one name: `tadah train` then stopped at an error that did not name the separator (`Mismatch between elements in datasets and ATOM ...`, `Type "Cut_Cos,Cut_Tanh" ... is not registered`). The index lists (`INDEX`, `FIXINDEX`: `INDEX_PATTERN`, now a comma-separated list of entries) keep their commas, which their readers split at (`13,14`, `13, 14` and `13 14` are one list, as before); a `+` between two entries is refused. A refused line names the separator and the line to write when blanks make its value valid (`CoreUserConfigParser::misusedSeparators`, which MLIP's TaskFactory uses for command-line values): `Invalid value for key FIXWEIGHT on line 3 of config.train: '0.1,0.2' separates values with ',', which a configuration line is not split at (values are separated by blanks: FIXWEIGHT 0.1 0.2)` (`'+'`, or `',' and '+'`); another is refused as any value the key's types do not take (`SBASIS 1,2`, `MODEL M_KRR Kern,Linear 2`: `Invalid value for key SBASIS on line 1 of config.train: '1,2'` and the key's schema, format and examples). A `+` is an exponent's sign, and stays in its number, only after an e or an E that follows a digit or a point and before a digit (`1e+5`); after a name or a word that ends in e it is a separator (`TYPE2B D2_Blip 4 4 Fe+Fe`, `DIMER true+1.0 false`), which got `Invalid schema for key: <KEY>` (every `+` after an e or an E was taken for an exponent's sign). `MODEL M_BLR,BF_Linear`, refused before as `Invalid schema for key: MODEL`, now names the comma. Tests: `test_blueprint_validator.cpp` (`Blueprint lists are separated by blanks, as the parser splits a line`, `Long lines: values are separated by blanks, as on a short line`), `test_core_user_config_parser.cpp` (`a comma or '+' between values`, `a comma or '+' in a name`), `test_blueprint_names.cpp`, `test_context.cpp` (the two comma pins now expect the parser's refusal).
- **The blueprint validator decides a line in time linear in its length, and a line of 2048 characters or more by the rules of a short one.** `BlueprintValidator::validate` matched a line with std::regex, which before it refused a line tried every way of sharing each run of blanks between two values and every reading of a word (a STRING at any of its letters, `1e5` as a DOUBLE or a STRING, `11` as an INT or a DOUBLE): a refusal took time exponential in the number of values, 4 to 8 s at 12 to 24 values (a `{DOUBLE}` list 2 blanks apart that ends in a word, a `TYPE2B` line with an odd element list, a `{STRING}` list that ends in a number) and longer than anyone waits beyond, as in 1.5.0. Lines of 2048 characters or more, where std::regex overflows the stack, took shortcuts with other rules: a line of numbers that strtod reads, between blanks or commas, was valid for every key (`{DOUBLE}` `.5`, `5.`, `inf`, `0x10`; `{INT}` `1.5`, `1e-310`), a `{STRING}` line was split at commas as well (`x1,2` refused for its part `2`), and the others (an index list with a step, `1-10:2, 12, ...`) went to std::regex. `validate` now splits a line into words at blanks and matches them against the blueprint compiled to a tree, carrying the set of word positions each part can end at from part to part (an `INDEX_PATTERN` list by a scanner of its grammar), with the rules of the type patterns, and the shortcuts are removed; `validateOnce` uses it too, and `getPattern()`/`getCaptures()` keep the anchored regex, which takes the same lines. Tests: `test_blueprint_validator.cpp` (`A line no blueprint takes is refused in linear time`, `Long lines are checked by the rules of a short line`, the `{INT}` section of `Long numeric lines`, and the pin `The validator takes the lines its blueprint regex takes`).
- **A `CONFIG` line with an inline comment** (`CONFIG config.train   # nested config`) includes the file it names. The parser kept the blanks before the `#` in the line, so the path was `config.train   `: `tadah train -c` and every other reader of such a file stopped with `Failed to open config file: config.train   `, and an include chain that was circular reported that error instead of the chain. The blanks before an inline comment are now dropped from every key line. Other keys were not affected: their values are read as whitespace-separated tokens.
- **199 of the 249 unit tests never ran under CTest.** The test name `histogram fixed-bin counts samples in [low, high)` has an unbalanced `[`, and the vendored Catch discovery script split the test listing through a CMake list, so that name and the 198 listed after it became one CTest entry. It matched no test case and still passed. With cmake-tools' discovery every test case is registered exactly once and an entry that matches nothing fails (`--warn NoTests`); all 249 run and pass. The explicit `core_pc_dataset_indices` entry, a workaround for this defect, is removed (its two cases are discovered).
- A `CoreUserConfigParser::parse` that threw (an invalid key or value, a missing `CONFIG` file) left the parser's recursion depth raised, so the next parse on that thread was treated as nested and did not reset its `CONFIG` chain. An RAII scope restores the depth on every exit.
- `is_number()` and `Checkpoint::get_dbl()` accept subnormal values, which the lossless writers produce (`1e-310`). `is_number()` rejected them, so the HPO WARM reader shifted every later dimension of the key, and a checkpointed subnormal read back as missing. Overflow is still rejected.
- **`tadah refit --rcut2b` and `--rcutmb` need `--retarget`** (`cli_needs` of `TASKS.refit.keys.retarget_rcut2b` and `retarget_rcutmb`), as `--pct`, `--set` and `--rhoform` do: a refit of an EAM file given either exited 0 and wrote the potential with its fitted cutoffs, the option having no effect and nothing saying so (also in 1.5.0); it is refused before any command runs (`--rcut2b requires --retarget`). Tadah.MLIP test: `Subcommand: refit: --rcut2b and --rcutmb require --retarget`.
- **`Matrix_Base::load` takes exactly rows × cols values, and `Matrix3d::inverse` refuses a matrix it cannot invert** (`maths.h`, C++ API). `load` given another number of values throws `std::invalid_argument` naming the count (`Matrix load: 11 values, but a 3 x 3 matrix takes 9`) and changes no element: a `Matrix3d` given 10 or 11 values overwrote elements it had set (the index wrapped back into the array), one given 12 or more wrote past its array, and one given fewer kept its other elements. `inverse` throws `std::domain_error` naming the determinant when it is 0 or not a finite number, or its reciprocal is not: it returned 1/0 times the cofactors, entries that are not finite numbers. Every caller in Tadah! passes nine values and refuses a singular cell before it inverts one. Test: `test_maths.cpp`.
- **`tadah analysis dataset_stats` takes `--dbfile` (`-d`) or `--structure` (`-s`) with `-c`** (`TASKS.analysis.dataset_stats.groups.input`: up to two options, `cli_needs` and `cli_excludes`): the configuration gives the cutoff of the statistics (the largest of its `RCUT2B` and `RCUTMB` values and the cutoff `RADIUS` of each `DESCRIPTOR` block), and the option gives the data in place of the configuration's `DBFILE` and `STRUCTURE` lines (`tadah analysis dataset_stats -c train.tadah -d test.tadah -o stats.tadah`). `--dbfile` and `--structure` need `-c`, refused before any data are read (`--dbfile requires --config`), and exclude each other (`--structure excludes --dbfile`). In Tadah! 1.5.0 neither option gave statistics: `-c` excluded both (`--dbfile excludes --config`), and without it the run read the data and stopped (`RCUTMAX is not set or <= 0`). Tadah.MLIP tests: `Subcommand: analysis dataset_stats -c with -d ...`, `... -c with -s ...`, `... refuses -d or -s without -c ...`, `... refuses -d with -s`.
- **`tadah hpo` without `--config` is refused at the command line, naming `--config`**: `--hpotarget` and `--validation` need `--config` (`cli_needs` of `TASKS.hpo.groups.input.keys.hpotarget` and `.validation`), as `--config` needs `--hpotarget`, so `tadah hpo --hpotarget config.hpo`, `tadah hpo --validation config.val` and `tadah hpo --check --hpotarget config.hpo` exit non-zero with `--hpotarget requires --config` (`--validation requires --config`) before any file is read, and the help of the group says `--config and --hpotarget are required; --validation is optional.`, followed by `[Between 2 and 3 of the following options are required]`; `tadah hpo` without options is refused asking for two (`Requires at least 2 options used but only 0 were given ...`). In 1.5.0 only `--config` needed `--hpotarget`: such a command line passed, and the run started on an empty training configuration (Tadah.MLIP's `Subcommand: hpo without --config is refused at the command line, naming --config`).

## [1.5.0] — 2026-09-10

### Changed
- Framework version bumped to `1.5.0` (`blueprint/blueprint_tadah.toml`), the single source every module's CMake `project(VERSION)` reads. The release is HPO-led; see the Tadah.HPO changelog for the three breaking changes it carries.

## [1.4.0] — 2026-07-14

### Added
- `EAMFAST` blueprint key (BOOL, explicit `default_value = ["true"]`): toggles the collapsed-EAM fast path in `pair_style tadah` for linear EAM-form models (see Tadah.LAMMPS changelog). `EAMFAST false` restores the bitwise generic kernel.

## [1.3.0-beta.1] — 2026-05-20

First public beta of the Tadah! framework. CORE consolidates the blueprint, configuration, and registry layers and introduces the long-running-job infrastructure (checkpoint + signal handlers) used by HPO.

### Added
- `RCUTENV` blueprint key — envelope cutoff for the new `DM_mBlipEnv` descriptor.
- Load-time data-transform and filter blueprint keys: `LSCALE` / `NO_LSCALE`, `ESHIFT` / `NO_ESHIFT`, `ESHIFT_ATOM`, `ESHIFT_DBATOM`, `EWEIGHT_TEMP`, `EFILTER`, `FFILTER`, `WDBFILE` / `WDBFILE_AUTO`, `ZERO_COM_FORCE`. These are applied during dataset load before training and persisted into `pot.tadah` for prediction round-trip.
- Per-species intercept layout in the blueprint schema (`bias` key now documents the one-hot intercept column behaviour required when `NORM=true` with `MODEL=BF_Linear`).
- Checkpoint and signal-handler infrastructure for long HPO runs.
- Container-style `begin()` / `end()` iteration on `Config`.
- `TADAH_ENABLE_ASAN` CMake option for AddressSanitizer builds.
- Single-source-of-truth versioning: `project(... VERSION ...)` is now wired from `blueprint/blueprint_tadah.toml` via the `tadah_read_version_from_blueprint()` helper in `cmake-tools`.
- **Bound-validation primitives**: blueprint adds `AUDIT` (off / warn / error; default off), `AUDIT_SAMPLE` (NN-sweep cap, default 256; `0` = full DB), `HEALTH_LOG` (per-iter monitor verbosity), and the analysis subcommands `TASKS.analysis.{dataset_stats, suggest_bounds, check_bounds}`. `Registry` exposes `view()` and `names()` so the audit can enumerate registered descriptors without instantiating them.

### Changed
- C++ standard upgraded from C++14 to **C++17**. A C++17 compiler is now required.
- Blueprint key casing: `atom` → `ATOM` (consistency with the rest of the schema; case-sensitive parsers will need to update).
- `TYPEMB` value-type regex generalised to accept the additional spherical-harmonics-order parameter; existing 2-UINT `TYPEMB DM_<name> <mu> <nu> <El1> <El2>` lines still parse, and the new 3-UINT example form `TYPEMB DM_<name> <l> <mu> <nu> <El1> <El2>` is documented.
- `WATOM` blueprint type/handling corrected; bundled `DM_*` examples updated to match.
- `THRESHOLD` lost its top-level default (was `1e-6`); the per-task `[TASKS.data.balance.keys.threshold]` default tightened from `["1e-1", "2e-2", "3e-3"]` to `["1e-4", "1e-5", "1e-6"]`. **This changes `tadah data balance` results when the user does not pass `THRESHOLD` explicitly.**
- `Context` output formatting improvements.

### Fixed
- `Registry` static-initialisation order across translation units — descriptors / cutoffs / models registered in different `.cpp` files no longer race the factory map at first use.

### Internal
- Substantive README rewrite.
- Community / governance pointer files (CONTRIBUTING / CITATION / SECURITY / CoC).
- CI/CD: lint stage (codespell) and tag-gated release-tarball stage added; `.gitignore` extended.
- Test build routed through `cmake-tools/cmake/TadahTesting.cmake` helpers (`tadah_declare_testing` / `tadah_add_tests`); replaces the hand-rolled `BUILD_TESTING` setup. Fixes a silent test-suite-disable on a bare reconfigure where the previous code captured `BUILD_TESTING` before the cache entry existed and FORCE-restored an empty value.

## [1.2.0] and earlier (condensed)

The `v1.0.0` → `v1.1.1` releases were the project's "internal playground" era. CORE was bootstrapped as the central blueprint + config + registry layer for the Tadah! framework, with the blueprint TOML schema iterating ad hoc across releases (typo fixes, type corrections, and key additions for descriptor and cutoff parameters). The blueprint TOML version was rolled to `1.2.0` during this period but no `v1.2.0` git tag was ever pushed; consider any release before `1.3.0-beta.1` undocumented in the modern Keep-a-Changelog sense.
