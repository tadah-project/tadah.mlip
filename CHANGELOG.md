# Changelog

This is the **umbrella changelog** for the Tadah! framework — the curated, cross-module view that users browsing the umbrella repository read first. Each entry is prefixed with the originating module:

- `[core]` — Tadah.CORE (blueprint / config / registry)
- `[mlip]` — Tadah.MLIP module (training / predict / data-balance orchestration)
- `[models]` — Tadah.MODELS (descriptors / cutoffs / basis functions / regressors)
- `[md]` — Tadah.MD (lightweight MD drivers)
- `[hpo]` — Tadah.HPO (hyper-parameter optimisation)
- `[lammps]` — Tadah.LAMMPS (`pair_tadah` LAMMPS plugin)
- `[umbrella]` — this repository (`tadah` binary, docs site, examples)

For the full per-module commit-level log, see each module's own `CHANGELOG.md`.

Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/);
versioning follows [SemVer](https://semver.org/) at the umbrella level.

## [Unreleased]

### Added
- `[hpo]` `tadah hpo` refuses at startup `OPTIM MPARAMS` on a function that reads no such value (`BF_Linear`, `BF_Polynomial2`, `Kern_Linear`, `Kern_Quadratic`, `Kern_LQ`, or an index past `Kern_RBF`'s sigma), on the `Kern_Polynomial` degree (an integer) and on a `Kern_RBF` sigma box that is not positive; and at its line `OPTIM` on an integer value (`SBASIS`) or an internal key (`ESTDEV`). See *Nested Fitting*, *Special cases*, and *Regressors*, *Non-linear models*.
- `[hpo]` `tadah hpo` refuses at startup `OPTIM RCUT2B` / `RCUTMB` on the cutoff of a `D2_EAM` / `DM_EAM` (inside a `D2_mJoin` / `DM_mJoin`, that descriptor's own value): the descriptor takes the cutoff of its setfl file and refuses another, so every candidate but the `-c` value failed its evaluation (FAILSCORE) and the run ended with status 0. The pre-flight audit and `tadah analysis suggest_bounds` no longer propose searching it. See *Nested Fitting*, *Special cases*.
- `[models]` `Function_Base::mparams()`, the `MPARAMS` a function reads; `shared_setfl()`, a setfl file parsed once per contents for every D2_EAM and DM_EAM of a process; `log_warning_once()`; `D_Base::cutoff_fixed_by()`, what fixes a value of a descriptor's cutoff key (the setfl file of D2_EAM and DM_EAM).
- `[umbrella]` Tests of the *Quick Start* example: `quickstart: in.ml with the shipped pot.tadah conserves energy and keeps the bcc crystal` (test_tadah, needs `TADAH_ENABLE_NFP`) runs `docs/source/quickstart/in.ml` with the shipped `pot.tadah` in-process and checks the total-energy drift (below 1 meV/atom), the temperature, the initial pressure, the potential-energy change and the bcc fraction after the run (common neighbour analysis); the 1.6.0 example failed every check. The guard `tadah_quickstart_reproduces_pot` (label `examples`) retrains the potential with `tadah train -c config.train` and with `tadah --task taskfile.txt` and checks that both have the keys of the shipped `pot.tadah` and predict the same energies, forces and stresses on `db.predict`, so the shipped file cannot go stale.

### Changed
- `[models]` The warnings descriptors give about their configuration (a knot past the cutoff, a bump past a `Cut_Dummy` cutoff, a non-compact basis with `Cut_Dummy`, a `DM_mEAD` or OrbitalWise `DM_Poly` channel function that is not rotationally invariant for L > 0: `DM_mRLR`, `DM_mSQRT`, `DM_mBlip`, `DM_mBlipEnv`, `DM_OW_*`/`DM_GOW_*` other than `_SQ`) are logged once per process, not once per descriptor object (tadah hpo builds the descriptors of every evaluation).
- `[hpo]` With `VERBOSE` > 0, the line a kernel prints when it is built (`Kern_RBF | sigma: ...`; `Kern_Polynomial`, `Kern_Sigmoid`, `Kern_Quadratic`, `Kern_LQ`) appears once per `tadah hpo` evaluation, which builds its model, where it appeared once per worker thread (a `Kern_RBF` run of 4 evaluations prints it 5 times, against 2).
- `[mlip]` **Removed: `Trainer::reinit()` and `DesignMatrix::refresh_context_scalars()`** (C++ API). Retrain a model in place with `model->reset_trained()`.
- `[umbrella]` **The *Quick Start* potential and LAMMPS example** (`docs/source/quickstart`). The potential is a smooth-cutoff `D2_Blip` pair term plus a `DM_mBlipEnv` embedding of a pair density (`Cut_Cos` cutoffs, `M_KRR Kern_Linear`, `STRESS true`), retrained on the same `db.train`, and `in.ml` builds bcc Ta at 3.30 Å, next to the potential's own lattice constant of 3.294 Å (EAM reference 3.304 Å). The 1.6.0 example ran a `D2_LJ` potential with a hard cutoff (`Cut_Dummy`, 6.5 Å) fitted to energies only, whose own bcc lattice is near 2.9 Å, on a bcc lattice of 3.5 Å: the run started at −74 GPa, the crystal tore into dense clusters at the fixed volume and the released energy heated it from 1000 K to about 8500 K, while the hard cutoff let the total energy wander by 35 meV/atom. The example now keeps the total energy within 0.08 meV/atom, cools from 1000 K to about 440 K (equipartition), starts at 0.1 GPa and stays bcc. A smooth-cutoff `D2_LJ` at its own lattice, the fix first proposed, was not used: no `D2_LJ` refit of these data holds bcc (C′ = (C11 − C12)/2 < 0 for each of `Cut_Dummy`, `Cut_Cos` and `Cut_PolyS` fitted to energies, energies and stresses, or energies, forces and stresses: −78 to −178 GPa over the nine fits, each at its own lattice constant of 2.93 to 3.06 Å). The new potential has no `EAMFAST` fast path (it is implemented for pure two-body and `DM_REAM` models only), so `pair_style tadah` runs the generic kernel: about 1 s per 1000 steps of the 250 atoms on one core, against about 0.2 s for the old potential on its fast path. The task file's `train` task includes `config.train` with `CONFIG` instead of repeating its keys. Docs: *Quick Start* explains the new keys and the effect of the stresses (the lattice constant is 3.380 Å fitted to energies only, 3.354 Å with `-F`), what to expect from `in.ml`, the fast path (its log line explained with the 1.6.0 `D2_LJ` potential) and what the example potential is and is not (a finite pair repulsion at short range, a spurious minimum of strongly compressed bcc near 2.25 Å, the timestep it needs above a few thousand K).
- `[core]` The `EAMFAST` description quotes its speed-up and log line for a `D2_LJ` potential (`RCUT2B 6.5`, `Cut_Dummy`) instead of the quickstart potential, and names `DM_REAM` as the only many-body descriptor with the EAM collapse.

### Fixed
- `[hpo]` **Every `tadah hpo` evaluation trains a model built from its own candidate.** A worker thread used to keep the model of its first evaluation and rewrite only the searched keys for the next ones, so what the model, its kernel and its design matrix read when they were built kept the first evaluation's value. `OPTIM EWEIGHT`, `FWEIGHT` and `SWEIGHT` (every model) and `OPTIM MPARAMS` (M_KRR kernels) were not applied after a worker's first evaluation, while every potential recorded the candidate's values; `OALGO 3` potentials gained one `SIGMA` per evaluation, and `tadah predict --error` on such a `best_pot.tadah` corrupted the heap; an M_KRR `-c` potential with `WEIGHTS` failed the first evaluation; and a second `TASK hpo` of a task file trained the first task's model (its `LAMBDA`, `FWEIGHT`, `FORCE`, ...). **Re-run a search that used `OPTIM EWEIGHT`, `FWEIGHT`, `SWEIGHT` or `MPARAMS`:** its reported optimum was never applied. The environment variable `TADAH_HPO_FORCE_REBUILD` is gone. Still carried over from a process's first run: the width of the worker pool (`THREADS`) and the evaluation counter (a second run's `ITERATION` numbers and `DUMP` names follow the first run's) (*Nested Fitting*, *Two runs in one process*).
- `[hpo]` **Every `tadah hpo` run starts its `PC_LAMMPS --hotvar` values from their `<initial>` value or its `WARM` seed.** The values each evaluation hands to the next were kept for the process, so the second `TASK hpo` of a task file started each hot script from the value the first run's last evaluation converged to, and did not reproduce the same run made alone (example `01_minimal` at `MAXEVAL 3`: `TOTAL_LOSS/N` 1.043183703093665e-01 against 1.043183703095260e-01); its files are now those of the run alone but for the evaluation numbers. See *Nested Fitting*, *Two runs in one process*.
- `[models][mlip]` **`SIGMA` belongs to the fit that computed it.** `tadah train -c pot.tadah` with an `OALGO 3` potential wrote the new `SIGMA` after the old one (34 values for 4 weights, and `tadah predict --error` then corrupted the heap); a retrain without `OALGO 3`, or with every weight pinned, kept the old one beside the new weights, and `predict --error` used it. A fit now replaces the `SIGMA` of its configuration, a fit that computes none writes none, and `predict --error` refuses a `SIGMA` without N×N+1 values, naming N and both counts.
- `[models]` **`tadah train -c` with an M_KRR potential trains it** (exit 1, "This object is already trained!", when the potential had `WEIGHTS`). An M_KRR potential is written without `DBFILE`; add it to train from one.
- `[core][models]` **An integer read from a number-typed value is exact.** Where tadah reads an integer from a value the blueprint types as a number, such as the `Kern_Polynomial` degree (`MPARAMS (1)`), `2.0` or `2e0` is 2 and `2.7` or `2abc` is refused, naming the key and the value; it read the integer prefix (`MPARAMS 2.7` trained the degree 2). Keys typed as integers (`SBASIS`, `OALGO`, `VERBOSE`, `--uniform`, ...) take plain digits only and refuse `2.0` or `1e3` when the configuration or command line is read, as before. For C++ callers, every integer read of a `Context` (`get<int>`, `get<size_t>`, integer containers) takes an exact in-range integer in any spelling and refuses a fraction, trailing text or an out-of-range value (Tadah.CORE). `Kern_RBF` refuses sigma 0.
- `[core]` `Context::get(key, container)` refuses a key with more values than the container holds (it wrote past a `std::vector`).
- `[core]` **A `CONFIG` line with an inline comment** (`CONFIG config.train   # nested config`) includes the file it names; `tadah train -c`, `tadah --task` and every other reader stopped with `Failed to open config file: config.train   `, the blanks before the `#` kept in the path. Comments on the other keys were not affected.
- `[mlip]` **`tadah data print`, `tadah analysis descriptor` and `tadah analysis bfunc` take `-i` strictly**, as `data sample`, `balance` and `write` do: 1-based indices checked against the structures of the DBFILE (for `bfunc`, the basis functions of the descriptor) before anything is read, an index outside them, `0`, a descending range and a malformed entry refused naming it (`tadah data print: index 9 (in '4-9') is outside 1-5 (the dataset has 5 structures)`), and several values one list (`-i 1 3`). `analysis descriptor -i` refused every index above 1 since 2025-04 (every release from 1.0.0), the help's own example `--index 1,3,5` included, and crashed (`-i 5-2`, `-i 1 3`) or hung (`-i 0`); `data print -i` dropped indices past the end (`-i 4-9` printed two structures, exit 0) and did not finish in two minutes on `-i 1-3000000`; `analysis bfunc -i` dropped an index past the last function with a WARNING and printed a function from outside the grid for `-i 0`. Tests: the `Subcommand: data print -i`, `analysis descriptor -i` and `analysis bfunc -i` cases (test_tadah), `test_dataset_tools.cpp` (MLIP).
- `[mlip]` **A structure without atoms counts as a structure for `-i`** (its blank line straight after the stress lines, as `tadah data print -d` and `data sample` read it): `StructureDB::count` stopped at the first such structure, so `tadah data write -i` refused every later index with a false count (`index 3 is outside 1-1 (the dataset has 1 structures)`). `data print -i` and `analysis descriptor -i`, which take their bound from it too, read the selected structures in one pass and parse only those, so a structure that is not valid elsewhere in the file does not stop them. ## [1.6.0] — 2026-09-25

A clean-up release for wider testing: one version everywhere, documentation that matches the code, and a set of small nested-fitting fixes.

**BREAKING for DM_REAM potentials:** the density form `RHOFORM` is mandatory; add `RHOFORM SIGNED` to a DM_REAM potential or configuration written before 1.6.0 to use it unchanged (see *Changed*).

**Behaviour change for bounded gradient searches:** `tadah hpo`'s finite-difference gradients no longer evaluate outside the `OPTIM` box, with either step rule (`PARAM fd_kernel inhouse` or `ceres`); within a step of a bound they are one-sided, so a search whose gradient reaches a bound can take a different path, and a box too narrow for the step, `diff_method 2` (RIDDERS) and finite-difference settings that never take effect (the `NOISE` block's `AUTO` included) are refused at startup (see *Changed*).

**NLopt's `MAXEVAL` counts every evaluation:** each loss, each finite-difference point and each analytical gradient, as with `DLIB:BFGS` and CERES; an NLopt gradient search made up to about twice `MAXEVAL` evaluations, and an `ANALYTICAL` one up to `MAXEVAL` losses and as many gradients, so with the same `MAXEVAL` such a search now does less: raise `MAXEVAL` to keep the old totals. `GD_STOGO` and `GD_STOGO_RAND` now need `MAXEVAL`; `MAXTIME`, `STOPVAL` or `RESTART` alone is a startup error (see *Changed*).

**`tadah hpo`'s journal trailer says why the search ended:** `Optimiser status` names the stop (`DLIB:BFGS: MAXEVAL reached`, `TADAH:ANNEAL: STOPVAL reached`, `CERES:LBFGS: FTOL_REL reached`, NLopt's `MAXEVAL_REACHED -- …`) and `COMPLETED` is no longer written. A job script that looked for `COMPLETED` no longer matches: test `tadah`'s exit status, not the status text (see *Changed*).

**Check datasets converted by older versions:** the lattice vectors are the rows of a dataset's cell block. Datasets converted from a VASP OUTCAR or a CASTEP `.castep`/`.md`/`.geom` file before 1.3.0-beta.1 store the cell of a non-symmetric structure transposed, those converted from a `vasprun.xml` before 1.3.0-beta.1 have wrong positions, and VASP/LAMMPS/CASTEP files that `tadah data write -s` exported from a non-orthogonal CIF/COD entry before 1.6.0 have a transposed cell. `tadah analysis dataset_stats` lists the structures that can be affected; *Dataset Format* in the docs says how to repair them (see *Fixed*). Potentials and `tadah hpo` results fitted to affected structures need to be regenerated.

**Neighbour lists are exact for any cell:** every periodic image within the cutoff is now found for cells thinner than the cutoff in some direction, triclinic cells and atoms outside the cell (before, e.g., a 2-atom bcc cell with a = 3.41 Å at a 10 Å cutoff kept 168 of each atom's 180 neighbours). Training, `tadah predict` and `tadah hpo` change for such structures, and now agree with `pair_style tadah`; retrain potentials fitted to them (see *Fixed*).

**Re-convert VASP data:** the stored stress is the Cauchy stress in eV/Å³, positive under tension, from every reader, and the stored DFT energy is the free energy F, whose gradient the forces are. Datasets converted from a VASP OUTCAR or `vasprun.xml` by Tadah 1.0.0 to 1.5.x, or by a 1.6.0 development build without this change (the version number does not tell them apart), hold VASP's pressure sign (a `STRESS true` fit on them fitted the negated stress) and the energy without entropy (OUTCAR) or energy(σ→0) (`vasprun.xml`); re-convert them (*Dataset Format* in the docs says how to tell). CASTEP `.md` data converted by those builds still hold the kinetic stress; re-convert those too (see *Changed*).

## Migrating from v1.2.0 to 1.3.0-beta.1

> **Tag note.** No `v1.2.0` git tag was ever pushed; the most recent git tag in every module is `v1.1.1`. The blueprint TOML `version = "1.2.0"` field was bumped during the playground era but never tagged. In practice, "migrate from 1.2.0" means "migrate from `v1.1.1` head as of late 2025 / early 2026".

### Breaking changes

1. **`Cut_PT` normalisation (`[models]`).** The polynomial cutoff `Cut_PT` was previously off by a constant; it has been fixed to satisfy `f(0) = 1`. Any potential trained against v1.1.x with `RCUT_TYPE Cut_PT` will produce numerically different energies / forces / stresses on the new build. **Action:** retrain the affected potential, or pin the older Tadah.MODELS commit if reproducibility against an existing pot.tadah is required for your workflow.

2. **C++17 toolchain (`[core][mlip][models][md]`).** The minimum compiler standard moved from C++14 to C++17. **Action:** ensure GCC ≥ 7, Clang ≥ 5, or equivalent. CMake will fail at configure if the compiler is too old.

3. **Blueprint key casing: `atom` → `ATOM` (`[core]`).** The schema now uses upper-case `ATOM` consistently. **Action:** if you have hand-written input files using the lowercase form *and* you parse with a case-sensitive tool, capitalise. The Tadah! parser itself is case-insensitive for blueprint keys, so most users are unaffected.

4. **`set_project_name` CMake shim deprecated (`[umbrella]`).** Out-of-tree CMake users that called `set_project_name(...)` directly will see a deprecation warning. The shim still works as a one-line forward; it will be removed in a future release. **Action:** switch to `tadah_read_version_from_blueprint(TADAH_VERSION REQUIRED)` + standard `project(... VERSION ${TADAH_VERSION})`.

### Behavioural changes that don't break compilation but may change results

1. **`tadah data balance` defaults (`[core]`).** The `[TASKS.data.balance.keys.threshold]` default tightened from `["1e-1", "2e-2", "3e-3"]` to `["1e-4", "1e-5", "1e-6"]`. Runs that relied on the old defaults will now treat far more configs as outside threshold (and rescale them). **Action:** if you want the v1.1.1 behaviour, pass `THRESHOLD 1e-1 2e-2 3e-3` explicitly.
2. **`THRESHOLD` top-level default removed (`[core]`).** The top-level `THRESHOLD` ALLOWED_KEY no longer carries a `default_value = ["1e-6"]`. Tasks that previously inherited this default may now require an explicit value. **Action:** set `THRESHOLD` explicitly in your blueprint section if a task complains.
3. **`HPO best_pot` writer v2 (`[hpo]`).** The output layout differs from v1.1.1; downstream parsers should be re-validated. **Action:** re-run any post-processing scripts on a known fingerprint.
4. **`DM_mEAD` warning (`[models]`).** No behavioural change at runtime, but `DM_mEAD` with `L > 0` and `F ≠ F_SQ` now emits a load-time warning about its rotational-invariance defect. **Action:** ignore for legacy potentials; for new work, switch to a `DM_PS_*` descriptor.
5. **`TADAH_HPO_HOT_A0_*` and `TADAH_HPO_BAD_POT_ERMSE_*` env vars removed (`[hpo]`).** All five environment variables (`TADAH_HPO_HOT_A0_DEFAULT`, `TADAH_HPO_A0_MIN`, `TADAH_HPO_A0_MAX`, `TADAH_HPO_BAD_POT_ERMSE_MEV`, `TADAH_HPO_BAD_POT_ERMSE_REL`) no longer have any effect; the parser does not consult `getenv()`. **Action:** replace the `${hot_a0}` script convention with explicit `PC_LAMMPS --hotvar hot_a0 <min> <max> [<initial>]` on the producing line; replace `TADAH_HPO_BAD_POT_ERMSE_MEV=N` with `PC_ERMSE … --skip-above N`.
6. **`best_pot.tadah` warmstart-cache header (`[hpo]`).** The producer-side header line changed from `# HOT_A0 <script> <a0>` to `# HOT <script> <name> <value>` (multiple hot variables per script supported). Older `best_pot.tadah` files still parse on read for back-compat. **Action:** none for consumers; writers should expect the new format on subsequent runs.

### Deprecations
- `[models]` `DM_mEAD` with `L > 0` and `F ≠ F_SQ` — still works, prefer `DM_PS_*`.
- `[umbrella]` `set_project_name` CMake shim — still works, prefer `tadah_read_version_from_blueprint`.

### What's the same

All v1.2.0 / v1.1.1 blueprint inputs still parse (the `atom` / `ATOM` rename is handled case-insensitively by the parser, and `TYPEMB DM_<name> <mu> <nu> <El1> <El2>` still matches the 2-UINT regex form). Default behaviour is unchanged for `tadah train`, `tadah predict`, and the `pair_tadah` LAMMPS pair-style (other than the per-step bias precomputation, which only affects performance). Existing `pot.tadah` files load and predict; **only** potentials trained with `Cut_PT` will produce numerically different results — a retrain is the cleanest path forward. *Erratum (1.6.0):* 1.3.0-beta.1 also fixed the cell convention of the OUTCAR, CASTEP `.castep`/`.md`/`.geom` and `vasprun.xml` readers (the lattice vectors are the rows of `Structure::cell`), which changes the results of every structure with a non-symmetric cell; datasets converted before it may hold a transposed cell or wrong positions — see the 1.6.0 notes.

## [1.2.0] and earlier (condensed)

The `v1.0.0` → `v1.1.1` releases were the project's "internal playground" era. Substantive features landed across the modules in this period — DM_Blip, DM_mEAD, the regressor zoo, NLOpt-based HPO, the LAMMPS pair-style, MPI training, install-section docs reshuffles — but no curated, cross-module changelog was kept. The blueprint TOML `version` field was rolled to `1.2.0` during this period without a corresponding git tag. Treat anything before `1.3.0-beta.1` as undocumented in the modern Keep-a-Changelog sense; the per-module `CHANGELOG.md` files contain a one-paragraph era summary for each module.
